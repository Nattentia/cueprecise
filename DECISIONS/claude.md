## 2026-08-30 · YouTube cue 토큰은 병합 전체에서 한 번만 소비

**무엇:** 삽입한 라틴 토큰의 `(cue index, token index)`를 병합 전체에서
기록하고, 뒤의 공백 후보가 같은 자막 토큰을 다시 보더라도 삽입하지 않는다.

**왜:** 롤링 cue의 시간 범위와 탐색 lookahead가 인접한 두 Gemini 공백에
동시에 걸릴 수 있다. 텍스트 중복만 전역 차단하면 실제로 두 번 발화된 같은
용어까지 잃으므로, 소스 위치가 같은 토큰만 소비 완료로 처리한다. 합성 회귀
사례에서 같은 `API` cue가 두 공백에 2회 들어가던 결과가 1회로 줄었고, 실제
fixture 결과는 11단어로 변하지 않았다.

## 2026-08-30 · CAPTION_LOOKAHEAD 4.0 -> 0.5 (오탐 제거)

`merge.py` 는 CONTRACT 1절상 claude 소유 파일이나 PR #2 로 codex 가 구현해
main 에 머지했다. 소유권 위반이지만 결과물이 정상 동작하므로 되돌리지 않고
발견한 결함만 최소 수정한다. 위반 사실은 아래 별도 항목에 기록한다.

**결함:** `CAPTION_LOOKAHEAD = 4.0` 이 cue 탐색 범위를 공백 끝에서 4초까지
넓혀, 공백과 겹치지 않는 cue 의 토큰을 끌어온다.

재현 (`jcBDSLSeud4`, 공백 `[678.70, 680.70]`):

```

  676.88-681.15  '이런 식으로 답을 만들어내는 것을'   latin=[]
  679.20-683.23  'retriever먼트 제이션이라고'        latin=['retriever']

LOOKAHEAD=4.0 이 추가로 끌어온 cue
  683.24-688.83  'RG의 장점이 뭐냐? 모델이 그대로'    latin=['RG']
```

`RG` 가 삽입됐다. 두 가지로 잘못이다.

1. 해당 cue 는 공백 `[678.70, 680.70]` 과 겹치지 않는다. 683.24 는 공백

   `RG` 를 중복 삽입하는 셈이다.

**수정:** `CAPTION_LOOKAHEAD` 를 `CAPTION_LOOKBACK` 과 같은 0.5 로 낮춘다.
롤링 자막이 발화보다 늦게 뜨는 지연을 흡수할 여유는 남기되, 공백과 무관한

## 2026-08-30 · overlap을 포함한 실제 청크 길이를 상한 이하로 검증

**무엇:** 먼저 `ceil(total/chunk_max)`로 균등 계획하되, 첫 청크 이후에
overlap을 더한 실제 추출 길이가 상한을 넘으면 청크 수를 하나씩 늘린다.
모든 청크는 16kHz mono 64kbps MP3로 만들고 입력 SHA-256과 계획을 원자적으로
`job.json`에 저장한다.

**왜:** 3,570초 입력을 1,790초 상한으로 둘로 나누면 core는 1,785초지만
두 번째 청크에 overlap 10초가 더해져 1,795초가 된다. 단순 ceil만 믿으면 API
상한을 다시 넘으므로 실제 start/end를 만든 뒤 상한을 재검증해야 한다.

## 2026-08-30 · 호출량은 서버 quota가 아닌 보수적 로컬 추정치

**무엇:** API key의 SHA-256별, Pacific 날짜별로 실제 요청 직전 시도 횟수와
최근 1분 시각을 file lock 안에서 원자적으로 기록한다. 일일/RPM 한도는 호출자가
반드시 설정하며 코드에 특정 무료 한도를 기본값으로 넣지 않는다.

**왜:** 실패와 429도 서버 quota를 소비할 수 있고, 다른 도구가 같은 key를 쓴
호출은 이 원장에서 볼 수 없다. 따라서 성공 후가 아니라 요청 직전에 올리고,
화면에는 항상 `local estimate`라고 표시해야 한다.

## 2026-08-30 · 청크 화자는 overlap 다수 증거로만 연결

**무엇:** 첫 청크의 raw label은 등장 순서대로 내부 global label을 부여한다.
다음 청크는 같은 절대 시각·같은 단어가 최소 2개 겹치고, 1위 표가 단독일
때만 local→global을 `inferred/overlap`으로 연결한다. 두 local label이 같은
global을 요구하면 강한 한쪽만 받아들이고 나머지는 `unresolved`로 둔다.

**왜:** 호출마다 `spk:0`과 `spk:1`이 바뀔 수 있다. raw 번호를 직접 합치면
청크 전체 화자가 뒤집히므로, `speaker_raw`는 불변 보존하고 증거 부족 시 기존
reader용 `speaker`만 raw로 유지한다. overlap 중복 단어는 derived 결과에서만
제거하고 제거 수를 metadata에 남긴다.

## 2026-08-30 · 단어 하나가 깨졌다고 청크 전체를 버리지 않는다

**실행:** `vRTcE19M-KE` (58분 05초, 영어 강의) 2청크 실행. chunk 0 성공
(5309단어). chunk 1 실패.

```
TranscriptionResultError: word_info[3341] 'language'의 timestamp가 비정상입니다: start=1119.8, end=120.3
```

**원인:** Gemini 가 긴 오디오에서 비결정적으로 단어 하나의 offset 을 손상시킨다.
같은 `chunk-001.mp3` 를 같은 설정으로 다시 요청하니 5288단어 전부 정상이었고
(`end<start` 0건, 단조증가 위반 0건), 그 단어는 `1119.8-1120.3` 이었다. 즉
원본은 `1120.3` 인데 앞자리 `1` 이 누락돼 `120.3` 으로 왔다. 코드 결함이 아니라
상류 API 의 산발적 결함이다.

**설계 문제:** `2026-08-30 · 전사 응답은 word timestamp 계약을 엄격히 검증`
항목이 첫 이상 단어에서 청크 전체를 중단시킨다. 그 판단의 근거("빈 응답을
조용히 저장하면 다음 단계에서 원인을 못 찾는다")는 지금도 맞다. 다만
**5,300단어 중 1건**에도 같은 잣대를 댄 것이 과했다. 게다가 응답 원문을
어디에도 남기지 않아, 이미 소모한 호출 결과가 통째로 사라졌다. 실패 1건이
호출 2회(실패 + 재실행)를 먹고, 재실행도 같은 확률로 또 깨진다.

**수정 — 세 가지. 호출을 늘리지 않는 것이 제약이었다.**

1. **응답 원문을 파싱 전에 저장한다.** `transcribe.request_raw` / `parse_raw`
   로 호출과 파싱을 분리하고, `transcribe()` 가 `raw_path` 를 받으면 검증 전에
   `chunk-NNN.raw.json` 을 쓴다. 파싱이 실패해도 소모한 호출이 남는다.
   29분 청크 기준 0.9MB (source.mp3 64MB 대비 무시할 수준). 덤으로 지금
   버리던 Gemini 부가 정보가 보존돼, 나중에 필요해지면 호출 없이 꺼낸다.
2. **깨진 timestamp 를 이웃으로 복구한다.** `end < start` 면 다음 단어의
   start 를, 그게 없으면 `start + cap` 을 쓴다. `cap` 은 그 응답 안 정상
   단어들의 p99 길이라 응답마다 자체 보정된다. `start` 역행·누락·음수도
   앞 단어의 end 로 되돌린다. **단어는 지우지 않는다.**
   실측 근거: 이 응답에서 앞 단어 end == 다음 단어 start 가 89.7%(4742/5287),
   단어 길이 중간값 0.20초·최대 1.50초. 관측 사례에 적용하면
   `min(다음 단어 start 1120.3, 1119.8+cap)` = **1120.3** 으로 정답과 일치한다.
3. **무더기 손상은 여전히 중단한다.** 보정이 `max(3, 단어수의 0.5%)` 를
   넘으면 `TranscriptionResultError`. 산발적 잡음과 체계적 손상을 가른다.
   이때도 원문은 저장돼 있어 원인 조사에 호출을 다시 쓰지 않는다.

**저장된 응답 재사용 경로.** 위 1번만으로는 "복구 가능"에 그친다. 호출 0회로
실제 되살리려면 재파싱 경로가 있어야 한다. `transcribe.from_raw()` 와
`pipeline._reusable_raw()` 를 넣어, 미완료 청크에 쓸 수 있는 원문이 있으면
API 대신 그것을 파싱한다. 쿼터 preflight 도 실제 호출할 청크 수만 센다.
요청 언어가 다르면(`requested_langs` 비교) 재사용하지 않고, `--force` 는
무시한다. 재파싱마저 실패하면 임의로 호출하지 않고 "원문 파일을 삭제하고
재실행하라"고 안내한다. 쿼터 소비는 언제나 사람이 정한다.

`google-genai` 임포트를 `request_raw` 안으로 옮겼다. 파싱·복구·재사용은
SDK 없이 돌아가고, `pipeline.py` 의 지연 임포트도 필요 없어졌다.
`transcribe.py` 단독 실행도 `--from-raw` 를 받는다.

**보정 흔적은 숨기지 않는다** (CONTRACT §6). 보정된 단어에
`timestamp_repaired: ["end"]`, 페이로드에 `timestamp_repairs` 목록(index/
text/field/from/to), `speakers.reconcile_chunks` 가 이를 `chunk_index` 를
붙여 derived 까지 옮긴다. `pipeline` 은 `청크 N: M단어, timestamp 보정 K` 를
찍는다. 전부 optional 필드라 CONTRACT 개정은 필요 없다(§6).

## 2026-08-30 · bundle 용량 실측 — 범인은 영상이 아니라 오디오다

소유자가 "로컬에 영상까지 들이면 무겁지 않냐" 고 물어 실측했다.

| 항목 | 23분 | 58분 |
|---|---|---|
| `source.mp3` | 26.8MB **48%** | 61.5MB **56%** |
| `raw/audio/` 청크 | 10.7MB 19% | 26.7MB 24% |
| `source.mp4` 영상 | 15.9MB 28% | 14.4MB **13%** |
| 나머지 전부 | 2.4MB 5% | 7.6MB 7% |
| **합계** | **55.8MB** | **110.3MB** |

**오디오가 72~80% 다.** 영상은 13~28% 로 셋 중 가장 작다. 전사·자막·프레임·
색인을 다 합쳐도 5~7% 라 무시해도 된다. 영상을 뺄 이유가 없다는 뜻이다.

낭비는 두 군데였다.

1. **오디오를 두 벌 갖고 있다.** `source.mp3` (48kHz 스테레오 160kbps) 를
   `chunk` (16kHz 모노 64kbps) 로 변환해 둘 다 보관한다. Gemini 는 아래쪽만
   본다. 23분 영상은 청크가 1개뿐이라 전체 오디오의 완전한 사본이다.
2. **mp3 변환이 파일을 키운다.** yt-dlp 가 받는 것은 m4a 129kbps 21.7MB
   인데 `--audio-format mp3 --audio-quality 0` 이 이를 mp3 160kbps 26.8MB 로
   바꾼다. **받은 것보다 5MB 크고**, 재압축이라 음질도 떨어진다.

## 2026-08-30 · 오디오를 받은 형식 그대로 둔다 (mp3 변환 폐지)

**무엇:** `-x --audio-format mp3 --audio-quality 0` 을 버리고
`-f "ba[protocol^=http]/ba/bestaudio"` 로 받은 스트림을 그대로 저장한다.
파일명이 `source.mp3` 에서 `source.<ext>` 로 바뀌므로 `audio.source_audio()`
가 `m4a → webm → opus → mp3` 순으로 찾는다.

**왜:** 변환이 순손해다. 파일이 커지고(21.7 → 26.8MB) 재압축으로 음질이
떨어진다. 어차피 청크를 만들 때 16kHz 모노 64kbps 로 낮추므로 원본을 고음질
mp3 로 보관할 이유가 없다. **Gemini 가 받는 것은 한 글자도 달라지지 않는다.**

**실측 (같은 영상, 같은 원어 트랙):**

| 영상 | 기존 mp3 | 원본 형식 | 절감 |
|---|---|---|---|
| `jcBDSLSeud4` (ko) | 26.8MB | opus 100k **17.6MB** | -34% |
| `vRTcE19M-KE` (en) | 61.5MB | opus 103k **44.7MB** | -27% |

`ba` 가 더빙 트랙을 고를까 걱정했으나 실측에서 원어를 정확히 골랐다
(`jcBDSLSeud4` → `ko`, `vRTcE19M-KE` → `en-US`). yt-dlp 가 원어 기본 트랙을
우선한다.

**기존 bundle 은 무효화되지 않는다.** `source_audio()` 가 `source.mp3` 를
계속 인식하고, `stage_fetch` 는 오디오가 이미 있으면 다시 받지 않는다.
따라서 fingerprint 가 그대로라 이미 분석한 영상을 다시 돌릴 필요가 없다.
이 점 때문에 "기존 bundle 무효화" 라는 예상 비용이 실제로는 0 이었다.

**이름 충돌을 막았다.** 오디오와 영상이 둘 다 원본 형식을 쓰면 webm 끼리
`source.webm` 으로 부딪힌다. 영상을 `source_video.<ext>` 로 옮기고
`visual.VIDEO_NAMES` 에 구 bundle 용 `source.mp4` 를 남겼다.

**안 한 것:** 더 낮은 비트레이트 포맷(139, 49kbps, 23분 8.2MB) 선택. 이론상
문제없지만(우리가 보내는 것은 16kHz 모노다) 전사 품질 영향을 실측한 적이
없고 확인에 Gemini 콜이 든다. 저장 공간이 실제 문제가 될 때 판단한다.

## 2026-08-30 · MCP 프로토콜 오염 (stdout 을 로그와 공유했다)

`pipeline._log` 가 `print()` 로 stdout 에 쓰고, `fetch_youtube.fetch` 는

실제 MCP 클라이언트는 이 줄들을 파싱하지 못해 끊긴다. 7개 도구 중
`ytx_register` 만 해당하지만 그것이 시작점 도구다.

**수정:** `_log` 를 stderr 로 보내고, `fetch_youtube.fetch` 가 yt-dlp 출력을
삼키도록 했다(실패 시 stderr 를 예외 메시지에 담는다). CLI 사용자는
터미널에서 그대로 보이므로 달라지는 것이 없다. 요약 JSON 만 stdout 에 남는다.

**검증:** 같은 호출을 다시 하니 stdout 오염 0건, 진행 로그는 stderr 로 갔다.
회귀 테스트 2건을 넣었다 — `_log` 가 stdout 에 아무것도 안 쓰는지,
`serve()` 가 내보내는 모든 줄이 JSON 으로 파싱되는지.

## 2026-08-30 · 세션 종료 전 검토에서 잡은 두 가지

소유자가 "이번에 많이 했으니 한 번 더 검토하라" 고 해 main 대비 전체 diff 를
다시 읽었다. 두 건이 나왔고 둘 다 고쳤다.

### `--force` 가 옛 원본을 남겨 용량을 두 배로 만든다

구 bundle 에서 `--force` 로 다시 받으면 `source.mp3` (26.8MB) 는 그대로 둔 채
`source.webm` 을 새로 받는다. `source_audio()` 가 webm 을 고르므로 동작은
하지만 mp3 가 영원히 남는다. 영상도 `source.mp4` + `source_video.mp4` 로
같은 문제다. **용량을 아끼려고 한 변경이 오히려 두 배로 만드는 셈이다.**

`_remove_stale_sources()` 로 다시 받기 직전에 이전 원본을 지운다. 다시 받는
자리이므로 잃는 것이 없다. 실측: force 후 raw 에 `source.webm` 16.8MB +
`source_video.mp4` 15.9MB 만 남고 고아 파일 0.

### 저장된 응답을 언어만 보고 재사용해 타임스탬프가 어긋날 수 있다

위 수정을 검증하다 더 깊은 문제가 보였다. `--force` 로 오디오 형식이 바뀌면
길이 측정이 미세하게 달라져 청크 경계가 옮겨갈 수 있다. `--chunk-max-secs`
를 고쳐도 마찬가지다. 그런데 `_reusable_raw` 는 `requested_langs` 만
비교했다. 경계가 달라진 뒤 남아 있는 옛 응답을 그대로 붙이면 **다른 구간의
전사가 조용히 들어가고 타임스탬프가 어긋난다.**

재현 조건: `--force` 로 다시 받아 재계획 → 모든 청크가 `planned` 로 돌아가
pending 이 됨 → 다음 실행에서 옛 raw 를 재사용. 전사가 이미 완료된 bundle
에서는 pending 이 없어 이 경로를 타지 않으므로 지금까지 드러나지 않았다.

응답 원문에 꼬리표를 함께 저장한다: `fingerprint`, `chunk_index`,
`chunk_start`, `chunk_end`, `requested_langs`. 하나라도 다르면 재사용하지
않고 다시 호출한다. 꼬리표가 없던 시절의 응답도 여기서 걸린다.

**조용히 틀린 결과보다 호출 한 번이 낫다.** 원문은 그대로 남으므로
`transcribe.py --from-raw` 로 수동 복구할 수 있다.

**테스트:** 160건 통과 (153 + 7). force 시 옛 원본 제거(구 이름 포함),
다른 파일은 건드리지 않음, 경계·입력 오디오·꼬리표 없음 각각에서 재사용

## 2026-08-31 · 자막 언어 고정을 푼다

**무엇.** `fetch_youtube.fetch` 가 `ko-orig` 를 박아 쓰던 것을 원어 자동자막
`.*-orig` 로 바꿨다. 없으면 일반 자막(ko/en)으로 한 번 더 시도한다. 받은
언어는 `captions.json.language` 에 남는다. 명시 지정도 가능하다
(`fetch(..., langs=["ja"])`, CLI `--sub-langs`).

**왜 지금인가.** 이 작업은 앞서 두 번 미뤄졌다. 이유는 "자막을 받아와도
`merge.py` 의 삽입 게이트가 한국어 조사 잔존을 보므로 영어 영상에서는 삽입이
0 이다 — 자막만 고쳐서는 아무것도 안 풀린다" 였다. 그 판단은 지금도 맞다.

바뀐 것은 자막의 두 번째 용도가 생긴 점이다. 번역문 가드(같은 날 항목)가
"원문이 무슨 언어인가" 의 근거로 자막을 쓴다. 영어 영상의 자막이 비어 있으면
그 영상에서는 가드의 근거 하나가 통째로 없다. merge 를 위해서가 아니라 가드를
위해 받는다.

**yt-dlp 문법.** `--sub-langs` 항목은 정규식으로 해석된다. `*-orig` 는
`Wrong regex for subtitlelangs` 로 거절당한다. `.*-orig` 가 맞다. 실측으로
확인했다.

## 2026-08-31 · 자막 폴백이 기계 번역을 물어오는 구멍을 막는다

**무엇이 문제였나.** 같은 날 넣은 자막 폴백(`ko,en`)이 `--write-auto-sub` 를
함께 켠 채였다. YouTube 는 자동자막을 아무 언어로나 기계 번역해 준다. 영어
영상에 `ko` 를 요청하니 실제로 한국어 번역 자막을 내려주기 시작했다
(`Writing video subtitles to: vRTcE19M-KE.ko.vtt`, 이어서 429 로 중단).

**왜 위험한가.** 번역문 가드가 자막을 "원문이 무슨 언어인가" 의 근거로 쓴다.
영어 영상에 한국어 번역 자막이 붙으면 가드가 **멀쩡한 영어 전사를 번역문으로
오판해 전사를 막는다.** 없던 실패가 새로 생긴다. merge 쪽은 삽입 게이트가
전사의 한국어 조사를 보므로 영향이 없다.

**고친 방법 둘.**

1. 폴백은 `--write-auto-sub` 없이 사람이 올린 자막만 받는다. 원어 트랙
   (`.*-orig`)을 받을 때만 자동자막을 요청한다.
2. `captions.json` 에 `original` 플래그를 남긴다. `-orig` 가 아니면 false 다.
   가드는 `original` 이 참인 자막만 근거로 쓰고, 아니면 요청 언어 규칙만
   본다. `language` 가 없던 시절 파일은 `source` 에서 유도한다.

**남은 한계.** 가드는 한국어만 안다. 일본어 영상이 영어로 번역돼 와도 잡지
못한다. 지금 쓰는 영상이 한국어와 영어뿐이라 그대로 둔다. 필요해지면
`_hangul_share` 를 문자 체계 표로 넓히면 된다.

**테스트:** 219 → 232. **Gemini API 호출:** 0회.

## 2026-09-01 · 이름을 CuePrecise 로 옮긴다

소유자 지시. 제품명 **CuePrecise**(한글 큐프리사이스), 저장소 `cueprecise`,
배포 이름 `cueprecise-mcp`, 명령 `cueprecise` / `cueprecise-mcp`, 설치 파일

### 바꾸지 않은 것과 그 이유

이 작업의 어려움은 이름을 바꾸는 것이 아니라 **바꾸면 안 되는 것을 골라내는
것**이었다. 네 가지를 그대로 뒀다.

- **Inno Setup 의 `AppId` GUID.** 이 값이 0.1.0 과 같아야 기존 설치가
  업그레이드로 인식된다. 바꾸면 제어판에 프로그램이 둘로 남는다.
- **`summary.py` 의 `META_PREFIX` (`<!-- ytx-summary:`).** 이미 저장된 요약
  첫 줄에 박혀 있는 표식이다. 바꾸면 0.1.0 이 만든 요약을 못 읽는다. 요약은
  전사에서 재생성되지 않는 유일한 자료다 (14절). 사용자에게 보이지 않으므로
  브랜드와도 무관하다.
- **데이터 폴더 `~/.ytx/data`.** 이미 있으면 계속 쓴다. 옮기는 이득은 폴더
  이름뿐인데, 중간에 실패하면 사용자의 영상 자료가 반쪽이 된다. 판정은
  `configuration.default_bundle_root()` 하나가 한다. 새 설치만
  `~/.cueprecise/data` 를 만든다.
- **DECISIONS 의 과거 기록.** 옛 이름이 나오는 문장을 소급해서 고치지 않았다.
  결정 기록은 그때 무엇을 알고 무엇을 정했는지의 장부다.

### 깨질 뻔한 곳 — 설정 이관

`setup_claude` 는 원래 `api_key` 가 없으면 `env` 를 통째로 빼고 썼다. 이름만
바꾸고 그대로 뒀으면, 설치 프로그램이 기존 항목을 옮기는 순간 **저장돼 있던
`GEMINI_API_KEY` 가 사라진다.** 이전 항목의 환경변수를 물려받도록 고쳤다.

같은 이유로 세 가지를 더 넣었다.

- `is_managed_server()` — 우리가 만든 항목인지 판정한다. 남이 `ytx` 라는
  이름을 쓰고 있을 수 있다. 우리 것이 아니면 옮기지도 지우지도 않는다.
- `--migrate` — 설치 프로그램이 조용히 부르는 이관 경로. GUI 를 열지 않고
  네트워크도 쓰지 않는다. 연결된 적이 없으면 아무 일도 하지 않는다.
  이것이 먼저 돌기 때문에 `[InstallDelete]` 로 옛 실행 파일을 지워도 연결이
  끊기지 않는다.
- 제거는 `cueprecise` 와 `ytx` 중 **우리가 만든 항목만** 지운다.

### MCP 도구 이름

`ytx_*` → `cueprecise_*`. `tools/list` 는 새 이름만 알리고, `dispatch` 가
옛 이름을 받아 옮긴다. 목록에 둘 다 실으면 호스트가 같은 도구를 두 번 본다.

## 2026-09-01 — 여러 MCP 클라이언트로 넓히기 (P0: 레지스트리)

0.1.1 까지는 Claude Desktop 하나만 상대했다. Codex, Claude Code, VS Code 를
붙이려면 앱마다 다른 것을 다뤄야 하는데, 그때마다 `setup_claude` 를 복사하면
"남의 설정을 건드리지 않는다"는 규칙이 사본마다 갈라진다. 그래서 규칙은
한 함수에 두고, 앱마다 다른 값만 `ClientTarget` 으로 뽑았다.

- `setup_file_client` / `remove_file_client` — 규칙을 담은 하나뿐인 자리.
  `servers_key` 를 받는다. **VS Code 는 최상위 키가 `mcpServers` 가 아니라
  `servers` 다** (실측 확인).
- `setup_claude` / `remove_claude` — Claude Desktop 을 가리키는 얇은 이름으로
  남겼다. `installer_support` 와 `cueprecise_cli` 가 이것을 부른다. 부르는
  쪽을 한꺼번에 고치면 무엇이 깨졌는지 알 수 없다.
- `ClientTarget.is_installed()` 는 **읽기만 한다.** 설치되지 않은 앱의 설정
  폴더를 만들지 않는다. 안 쓰는 앱 폴더를 남기지 않기 위해서다.
- `detector` 를 따로 둔 이유. Codex 와 Claude Code 는 설정 파일이 없어도
  설치돼 있을 수 있다. 그때는 `shutil.which` 로 봐야 한다.
- `resolve_clients(None)` 과 `all` 은 **감지된 앱 전부**다. 사용자가 앱 이름을
  몰라도 되게 하는 것이 이 작업의 목적이다.

CONTRACT 1절은 `src/configuration.py` 를 codex 소유로 적는다. 2026-08-30
개정으로 전권이 위임됐고, 커밋 #51 에서 같은 절차로 이 파일을 고쳤다.
codex 가 복귀하면 소유자가 다시 나눈다.

### 넣었다가 도로 뺀 것

`entry_extra`(항목에 얹을 값)와 `describe()` 를 먼저 넣었다가 지웠다. 부르는
쪽이 하나도 없었다. VS Code 는 `type` 을 쓰지 않고, Claude Code 의
`type: "stdio"` 는 자기 CLI 가 넣는다. `entry_extra` 는 오히려 `command` 를
덮을 수 있는 구멍을 스스로 만들고 그것을 막는 테스트까지 딸려 왔다. 쓰는
곳이 생기면 그때 만든다. `describe()` 는 doctor 가 무엇을 보여줄지 P4 에서
정한 뒤에 만든다.

### 실측으로 확인한 것 (문서가 아니라 이 PC 에서)

- `claude mcp add <name> [-s user] [-e K=V] -- <cmd> [args]`. **`-s` 기본값이
  `local`(프로젝트 스코프)이다.** 전역으로 붙이려면 `-s user` 를 줘야 한다.
  `~/.claude.json` 의 `mcpServers` 에 `type: "stdio"` 와 함께 쓴다.
- `code --add-mcp '<json>'` 은 `%APPDATA%/Code/User/mcp.json` 의 `servers` 에
  쓰고 `inputs: []` 를 같이 만든다. `type` 은 쓰지 않는다. **제거 CLI 가 없다**
  → 설치는 CLI, 제거는 파일 편집인 하이브리드가 된다.
- JSON 페이로드 안의 경로는 **슬래시로 써야 한다.** `code.cmd` 래퍼를 지나며
  백슬래시가 죽어 `Bad escaped character in JSON` 이 난다.
- 인자는 반드시 리스트로 넘기고 `shell=True` 를 쓰지 않는다. 쉘을 거치면
  `/c` 같은 인자가 경로로 오인돼 `C:/` 로 바뀐다.
- Codex 는 `codex mcp add/get/remove/list` 가 있어 TOML 을 직접 쓸 필요가 없다.
  CONTRACT 7절(외부 패키지 금지)을 지킨 채 붙일 수 있다.

### 여러 앱이 한 번들을 함께 쓰는 문제

붙는 앱이 늘어도 `bundle_root` 는 하나다. 두 앱이 같은 영상을 동시에 등록하면
같은 일을 두 번 하고 Gemini 를 두 번 쓴다. 자료가 깨지지는 않는다. 단계 산출은
`.tmp` 에 쓰고 `replace` 하며, 사용량 장부는 `usage._file_lock` 이 잠근다.
지금은 사용자가 CLI 와 Claude Desktop 을 함께 써도 나던 일이고, 앱이 늘면
확률만 올라간다. 막으려면 번들 단위 잠금이 필요하다. P0 범위가 아니다.

### 함께 넓어지는 위험 — `is_managed_server`

이 판정은 `args` 에 `mcp_server` 라는 글자가 있으면 우리 것으로 본다. 남이
자기 `mcp_server.py` 를 등록해 두고 이름까지 `cueprecise` 로 지었다면 오판한다.
전부터 있던 느슨함이지만, 상대하는 설정 파일이 하나에서 여섯으로 늘면 오판이
닿는 범위도 함께 넓어진다. P1 에서 조일지 판단한다.

### 안 하기로 한 것

원격 MCP 호스팅. ChatGPT 커넥터와 Claude.ai 웹은 HTTPS + OAuth 로만 붙는다.
거기 붙이려면 사용자 Gemini 키를 서버가 맡고 yt-dlp 를 서버에서 돌려야 한다.

## 2026-09-01 — 마지막 검토: 실패가 설치 화면을 빠져나가고 있었다

`SystemExit` 은 `Exception` 이 아니라 `BaseException` 이다. 설치 화면은

설정 파일이 깨져 있기만 하면 설치 화면이 조용히 멈춘다.

## 2026-09-01 — 전체 검토: 모킹이 가린 것

### VS Code 는 Windows 에서 한 번도 붙지 않았을 것이다

`subprocess.run(['code', ...])` 는 Windows 에서 실패한다. `code` 는 `.EXE` 가
아니라 `code.CMD` 이고, 이름만 주면 `FileNotFoundError [WinError 2]` 가 난다.
`_run` 이 그 `OSError` 를 잡아 "명령을 실행하지 못했다"로 바꾸므로, 사용자
눈에는 언제나 실패로 보였을 것이다.

테스트가 못 잡은 이유가 분명하다. 모든 테스트가 `subprocess.run` 을 가짜로
바꾼다. 인자를 어떻게 조립하는지는 전부 확인하면서, **그 명령이 정말 실행되는가**
는 아무도 보지 않았다.

`shutil.which` 로 찾은 완전 경로로 부르면 된다(실측). 인자를 리스트로 넘기는
방식 그대로 JSON 페이로드도 온전히 건너간다. 공백이 든 경로, 따옴표,
세미콜론까지 그대로 도착하는 것을 확인했다. 이름과 실행 파일 사이의 PATH 가
감지 시점과 실행 시점에 달라지는 일도 함께 막힌다.

`codex` 와 `claude` 는 `.EXE` 라 이름으로도 됐지만 같은 방식으로 통일했다.

### 모킹 없는 시험을 하나 넣었다

`RealLaunchTest` 는 이 PC 에 있는 명령을 실제로 띄운다. 설정 파일은 건드리지
않고 `--version` 만 부른다. 없는 앱은 건너뛴다. 이런 시험이 하나도 없어서
위의 버그가 살아남았다.

여기에 더해, 임시 `CODEX_HOME` 을 만들어 **진짜 `codex mcp add`/`remove` 로
등록과 제거를 태워 봤다.** 사용자 설정은 건드리지 않는다. 등록된 TOML 이
기대한 모양이고, 같은 파일에 있던 남의 항목이 그대로 남고, 제거 후에도 남의
항목만 남는 것을 확인했다. 이 확인은 앱이 있어야 하므로 테스트로 넣지 않고
여기 적어 둔다.

## 2026-09-01 — P4: 감지와 붙이기를 잇는다

P0~P3 는 라이브러리였다. 앱을 찾을 줄도 알고 붙일 줄도 알았지만, 그 둘을 잇는
자리가 없어 사용자에게는 아무것도 달라지지 않았다. 그 자리를 만들었다.

- `installer_support.connect_clients` — 필수 도구 확인과 연결 시험은 앱 수와
  무관하게 **한 번만** 하고, 앱마다 붙인다. `connect` 는 Claude Desktop 하나를
  가리키는 얇은 이름으로 남아 기존 테스트가 그대로 통과한다.
- `installer_support.disconnect_clients` — 제거는 **감지되지 않은 앱도 살펴본다.**
  붙인 뒤 앱을 지운 사용자의 설정에 우리 항목이 남아 있을 수 있고, 남겨 두면
  그 앱을 다시 깔았을 때 없는 서버를 가리킨다.
- `cueprecise setup --client all|<이름들>`, `cueprecise doctor` 의 앱별 표.
- 설치 화면에 체크박스. 찾은 앱만 켜져 있고, 없는 앱은 잠근 채 보여 준다.
  하나도 없으면 그 이유를 적는다.

### 한 앱의 실패가 나머지를 막지 않는다

앱마다 사정이 다르다. 남의 동명 항목이 있거나, 명령이 PATH 에서 사라졌거나,
설정 파일이 깨져 있을 수 있다. 하나가 막혔다고 전부 포기하면 멀쩡한 앱까지
못 쓰게 된다. 그래서 앱마다 따로 잡고, **무엇이 되고 무엇이 안 됐는지 둘 다**
돌려준다. 완료 창도 성공만 알리지 않고 실패한 앱과 이유를 함께 적는다.

전부 실패하면 그때는 실패다. 하나도 못 붙였는데 완료라고 말하지 않는다.

### 앞서 P0 에 적어 둔 구멍을 막았다

`resolve_clients` 는 감지된 앱이 없으면 빈 목록을 준다. 그것을 그대로 성공으로
읽으면 "아무 데도 붙이지 않고 설치 완료"가 된다. `connect_clients` 와
`setup` 둘 다 빈 목록을 실패로 다룬다.

### `doctor` 의 합격 기준을 바꿨다

전에는 Claude Desktop 설정 하나만 봤다. 그대로 두면 Codex 나 VS Code 에만 붙인
사용자가 실패로 나온다. 이제 **어느 앱에든 붙어 있으면 합격**이다.

`client_report` 는 앱 하나의 사고가 나머지 진단을 가리지 않게 앱마다 따로 잡는다.
설정 위치조차 정할 수 없는 환경(HOME 이 없는 등)도 포함한다. 기존 테스트가
`os.environ` 을 비우고 도는 것을 보고 알았다.

## 2026-09-01 — 붙여 보지 못한 앱들의 위험 점검 (설치하지 않고)

Cursor·Windsurf·Gemini CLI 를 설치하지 않은 채, 이 PC 에서 확인 가능한 근거만으로
안 될 만한 곳을 짚었다.

### 고쳤다 — `CLAUDE_CONFIG_DIR`

`CODEX_HOME` 과 같은 함정이 Claude Code 에도 있다. 실측했다.

    CLAUDE_CONFIG_DIR=<임시폴더> claude mcp add ... -s user
    → File modified: <임시폴더>\.claude.json     (홈이 아니다)

무시하면 `claude mcp add` 는 옮겨진 곳에 잘 써 넣는데 우리는 홈을 읽고
"등록하지 못했다"고 말한다. **등록은 됐는데 실패로 보고하는** 상태다. 사용자가
몇 번을 눌러도 같은 말이 나오고 고칠 길이 없다. Codex 와 같은 방식으로,
설정 경로가 그 변수를 따르고 명령을 부를 때 그 변수를 되돌려 준다.
변수가 없는 평범한 환경에서 홈을 주입해도 같은 파일을 본다는 것도 확인했다.

### 안전이 확인된 것

- **VS Code 는 주석을 지우고 쓴다.** 주석이 든 `mcp.json` 에 `--add-mcp` 를
  걸어 보니 주석 없는 순수 JSON 으로 다시 썼다. 우리 제거 경로가 엄격한 JSON
  파서를 쓰는데도 깨지지 않는다.
- **Gemini CLI 의 `settings.json` 은 엄격한 JSON 이다.** 이 PC 에 실물이 있어
  파싱해 봤다. 최상위가 평평한 객체라 `mcpServers` 를 얹는 우리 방식과 맞는다.

### 남는 위험 — 고치지 않고 적어 둔다

1. **Cursor 와 Windsurf 는 자동 감지에서 빠질 가능성이 높다.** 둘 다 VS Code 처럼
   `cursor` / `windsurf` 셸 명령을 **사용자가 따로 설치해야** PATH 에 생긴다.
   설치하지 않은 사용자가 다수일 것이다. 그러면 앱이 있는데도 체크박스에
   잠긴 채 나온다. `--client cursor` 로 이름을 대면 붙으므로 막히지는 않는다.
   앱의 실행 파일 경로를 후보로 더 보면 나아지지만, 그 경로를 확인할 수 없는
   상태에서 추측해 넣으면 P3 에서 막았던 오탐이 되돌아온다. 실물을 만나면 정한다.
2. **손으로 주석을 적어 둔 `mcp.json`/`.cursor/mcp.json` 은 붙이기 전에 막힌다.**
   VS Code 자신은 주석을 지우지만, 사용자가 편집기로 적어 넣을 수 있다. 그때
   `read_config` 가 실패해 그 앱만 건너뛴다. 다른 앱은 계속 붙고 이유도
   보고되므로 조용히 틀리지는 않는다. 주석 제거기를 손으로 짜면 `https://`
   같은 문자열을 주석으로 오인하기 쉬워 지금은 넣지 않는다.
3. **VS Code Insiders 는 다른 폴더(`Code - Insiders`)와 다른 명령
   (`code-insiders`)을 쓴다.** 지금은 안정판만 본다. Insiders 만 쓰는 사용자는
   감지되지 않는다.
4. Cursor·Windsurf 의 설정 경로와 키 이름은 여전히 문서 기준이다. 틀렸다면
   그 앱에 붙지 않을 뿐, 남의 설정을 깨뜨리지는 않는다.

## 2026-09-01 — 남들은 어떻게 하나 찾아보고 고친 것

### Gemini CLI 는 파일이 아니라 명령이었다

`gemini mcp add` 가 있다. 우리가 `settings.json` 을 직접 쓰게 만들어 둔 것은
틀렸다. 문서상 문법은 이렇다.

    gemini mcp add [-s user] [-e KEY=value] <이름> <실행파일> [인자...]
    gemini mcp remove <이름> -s user

**`-s` 기본값이 `project`** 다. Claude Code 와 같은 함정이라 `-s user` 를 준다.

**구분자가 다르다.** `codex` 와 `claude` 는 `-- <실행파일>` 을 요구하는데 Gemini
CLI 는 구분자 없이 이름 뒤에 바로 받는다(문서 예시:
`gemini mcp add python-server python server.py --port 8080`). `command_separator`
를 두어 타깃마다 정한다.

직접 쓰지 않는 편이 나은 이유가 하나 더 있다. 이 PC 의 `~/.gemini/settings.json`
은 다른 도구가 관리한다. 우리가 쓰면 그 파일을 통째로 다시 쓰게 된다.

### 명령이 듣지 않으면 파일로 돌아간다

이 앱은 이 PC 에 없어 명령을 실제로 태워 보지 못했다. 인자 배치는 판마다 다를
수 있다. 그래서 `GeminiCliTarget` 은 명령을 먼저 쓰고, 등록되지 않았을 때만
설정 파일에 직접 쓴다. 성공 여부를 설정을 다시 읽어 판정하므로 되돌아갈 때를
정확히 안다. 문서가 틀렸어도 사용자는 붙는다.

**남의 항목 앞에서는 돌아가지 않는다.** 그것은 다른 방법으로 붙여서도 안 되는
실패다. 그래서 `ForeignEntryError` 를 따로 두어 "다시 해 볼 만한 실패"와
구분한다.

### 찾아본 것들과 우리 위치

- **FastMCP 는 자동 감지를 하지 않는다.** 사용자가 `fastmcp install cursor` 처럼
  앱 이름을 댄다. 지원도 Claude Desktop·Cursor·Claude Code 셋뿐이고 나머지는
  JSON 을 찍어 주고 알아서 붙이라고 한다.
- **mcp-dock 같은 다중 클라이언트 도구는 설정 폴더의 존재로 감지한다.** P3 에서
  오탐 때문에 버린 방법이다. 이 PC 에는 다른 도구가 만든 `~/.cursor` 와
  `~/.gemini` 가 있으므로 그 도구들은 여기서 헛짚는다. 우리 기준이 더 엄격하다.
- **Cursor 는 설치 딥링크를 공식 지원한다.**
  `cursor://anysphere.cursor-deeplink/mcp/install?name=<이름>&config=<base64>`.
  FastMCP 가 Cursor 에 쓰는 방식이다. 사용자가 눌러 승인해야 하므로 조용한
  설치에는 못 쓰지만, **감지에 실패했을 때 링크를 건네는 폴백**으로는 맞다.
  아직 넣지 않았다.
- **Windsurf 는 명령이 없다.** 공식 문서상 방법은 마켓플레이스 UI, 명령 팔레트,
  그리고 `~/.codeium/windsurf/mcp_config.json` 직접 편집이다. Windows 경로도
  `%USERPROFILE%\.codeium\windsurf\` 로 우리가 쓰는 위치와 같다. 파일 방식을
  그대로 둔다.

### 시험 하나가 나머지를 가리고 있었다

`RealLaunchTest` 가 없는 앱을 만나면 `skipTest` 를 불렀는데, `subTest` 안에서
부르면 **그 시험 전체가 건너뛰어진다.** Gemini CLI 가 명령 방식이 되면서 이
PC 에 없는 앱이 목록에 들어오자 드러났다. 없는 앱은 미리 걸러 낸다.
